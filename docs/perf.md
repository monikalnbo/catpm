# catpm 性能实测（v0.5.5）

本文所有数字均为**本机同环境真实测量**，方法与样本数随每个表给出；跑不动或工具缺失的场景如实标注。测量日期：2026-11-10。原始数据：`logs/perf-final.log`；复现脚本：`scripts/perf_v10.sh`（版本间对照用**交错 A/B**：同一循环内交替跑两个版本，成对抵消系统漂移）。

## 测量方法

- **计时**：`date +%s%N` 纳秒墙钟；冷装场景每次用全新 `mktemp -d` 项目目录。每场景样本数随表标注（n=5 或 n=7），报中位数；版本对照另做逐对差值（paired delta）。
- **子进程画像**：本机无 strace/hyperfine，用 **PATH spy**（把 `curl`/`sha256sum`/`tar`/`cp`/`mv`/`rm` 包装成先记日志再 exec 原二进制的脚本，插到 PATH 最前）统计子进程调用；另做**时间戳 spy**（包装器记 `date +%s%N`）还原各阶段时间线。catpm 的全部子进程都走 PATH，画像完整。
- **对照工具**：apt（本机 dpkg，真实执行）、cargo（本机 rustc，真实编译）。cargo 对照用与本仓库生态同规模的依赖集（2 个小依赖：tinystr + cfg-if）。

## 与 apt 对比（本机实测）

| 操作 | apt | catpm v0.5.5 | 样本 |
|---|---|---|---|
| 刷新索引 | `apt-get update` **1913 ms** | `catpm update` **106 ms**（HTTPS 单源）/ 61 ms（本地源） | 各 n=5 |
| 冷装一个小包（含依赖） | `apt-get install --reinstall hello` **7134 ms** | `catpm add mathx`（2 包闭包，HTTPS）**301 ms** | apt n=5 / catpm n=5 |
| 已装列表 | `apt list --installed` **531 ms**（`dpkg -l` 30 ms） | `catpm list` **5 ms** | 各 n=5 |
| 查版本 | — | `catpm --version` **14 ms** | n=5 |

## 与 cargo 对比（本机实测，同规模依赖集）

| 操作 | cargo | catpm v0.5.5 | 样本 |
|---|---|---|---|
| `add`（只写清单） | `cargo add` **645 ms** | 并入 `catpm add`（写清单+装） | n=5 |
| 冷构建 2 依赖 | `cargo build` **12,374 ms** | —（catpm 装包即完成，不编译） | n=5 |
| 热构建 2 依赖 | `cargo build` **10,990 ms** | `catpm add`（全缓存命中重装）**122 ms** | n=5 |
| 冷装 2 包闭包 | —（等价物即 build） | HTTPS **301 ms** / 本地源 **158 ms** | n=5/7 |

注：cargo 的成本在编译（rustc 逐 crate），catpm 的成本在下载与校验子进程——工作量不同，对比目的是「装好一套能 import 的依赖」这一用户可感时延的量级差（30–40 倍）。

## v0.5.5 相对 v0.5.4：优化明细与如实结果

先画像（PATH spy）：v0.5.4 一次冷装 2 包 = 7 个子进程调用；v0.5.5 初版一度升到 14（并行化引入的 `cp` fork + 记账开销超过收益，交错 A/B 实测本地源反而慢 40 ms——已如实回退：**本地源回到进程内复制、零下载 fork**）。

定稿版 v0.5.5 的改动：

| # | 改动 | 效果 |
|---|---|---|
| 1 | **并行预取（仅 URL 源）**：解析完闭包后，单个 sh 脚本内并发起全部 curl（`&` + `wait`）；本地源不走 sh，用进程内 `copy_file` | 多包 HTTPS 冷装的串行下载变并发 |
| 2 | **批量哈希 + 进程内复用（`psha`）**：一次 `sha256sum f1 f2 …` 批量校验，哈希记在进程内存 `st`；`install_one` 见到本进程已验过的文件直接复用，不再逐包 fork | 每包省 1 次 sha256sum fork |
| 3 | **索引缓存路径 memo**：同一 root 的缓存文件名哈希每进程只算一次 | 每次运行省 1-2 次 printf\|sha256sum fork |
| 4 | **原子写跳过未变内容**：目标文件字节相同则不写不 mv（幂等重跑场景） | 重跑 add/update 省全部 tmp+mv fork |
| 5 | **合并 sh 调用**：清 stage+解包、删旧+换入 各并为一次 `sh -c` | 每包省 2 次 sh fork |

**定稿交错 A/B 结果**（同循环交替跑 v0.5.4 / v0.5.5，逐对差值）：

| 场景（本地目录源） | v0.5.4 | v0.5.5 | 差 |
|---|---|---|---|
| 冷装 2 包闭包 | 115–133 ms | 148–158 ms | **+30~40 ms（v0.5.5 慢）** |
| 冷装 6 包闭包（3 次 add） | 401–441 ms | 464–524 ms | **+60~90 ms（v0.5.5 慢）** |
| **冷装 2 包闭包（HTTPS raw 源）** | 298–341 ms | 268–301 ms | **−30~40 ms（v0.5.5 快）** |

**为什么本地源反而慢（如实记录，不掩饰）**：v0.5.5 的中断恢复（第 9 轮特性）给每次安装加了 4-6 次「写 tmp + mv」原子写与暂存解包的 fork——时间戳 spy 实测这些占 ~40-60 ms。这是**鲁棒性换时延的既定取舍**：v0.5.4 没有「被杀不留半写状态」的保证，v0.5.5 有。并行预取与批量哈希（本轮优化）在本地源上只是把这部分成本部分抵消（净 +30~40 ms 全部来自鲁棒性机制），在 HTTPS 源上净赚 30-40 ms（下载并发）。若只要速度不要中断恢复，可用 v0.5.4 二进制——但牺牲的是 kill -9 后磁盘状态的安全性。

**安全不变量**：`psha` 只在同一进程内复用预取阶段真实算出的哈希，不落盘（无可伪造工件）；换进程、未经过预取的文件、重新下载后的新字节都仍走真实 sha256sum。实测：篡改缓存（随机字节替换 .cpkg）仍被拦截并自愈重拉；`catpm fix` 六类残留清扫不回归；lock-exact install、remove+prune、outdated、sources 全部回归通过。

**没做的优化（如实记录）**：

- **不跳过幂等重装的重解包**：`add` 已装包时仍重跑 tar 解包（保留「重跑 add 修复损坏 deps/」的修复语义）。
- **不做下载字节级分片**：包体积 KB 级，单连接已够。
- **`lock`（纯解析）47 ms**：15 ms 进程启动 + 索引读取，接近地板，未再动。

## 环境与工具如实记录

- 本机 8 核 x86_64 Linux；测量时段系统近空闲（load < 0.7）；每组测量内两个版本交错执行以抵消漂移。
- 无 strace、无 hyperfine（不可安装）——fork 画像以 PATH spy 替代。
- cargo 侧「热」= 增量缓存保留、「冷」= 删 `~/.cargo/registry` + `target/`。
- apt 的 7134 ms 是 `--reinstall`（本机已有包的等价冷装途径）。
- 样本原始序列与逐对差值保存在会话工作区 `/tmp/perf/`（不入仓库）；仓库内 `logs/perf-final.log` 为成批中位数记录。
